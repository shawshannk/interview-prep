The interview framework

Most system design rounds run 45–60 minutes. Interviewers score structure, trade-off reasoning and depth more than the final diagram. Use this order and say out loud which step you're on.

StepTime (of 50 min)What you do
1. Clarify requirements5–8Functional scope (3–5 core features, what's out of scope); non-functional: scale, latency, availability, consistency, security/compliance, cost. Ask who the users are.
2. Estimate3–5Requests per second (average and peak), read/write ratio, storage per year, bandwidth. Round aggressively; the goal is the order of magnitude.
3. API3–5The main endpoints or events with key fields; idempotency for writes; pagination.
4. Data model5Entities, keys, access patterns, which store fits (relational, key-value, search, object storage).
5. High-level design8–10Clients, edge, services, data stores, queues; walk one request through the diagram.
6. Deep dives12–15The 2–3 hardest parts: hot spots, consistency, fan-out, failure handling. Often the interviewer picks; offer options.
7. Bottlenecks and trade-offs5What breaks first at 10×, single points of failure, monitoring, cost, what you'd do with more time.

Interview angle: state assumptions explicitly ("I'll assume 10 million daily users and a 100:1 read/write ratio"), offer two options with trade-offs before choosing, and connect choices back to the requirements. For Lead/EM roles, also mention rollout, migration, team ownership and operational cost.

  • Serial dependencies multiply: a service depending on three 99.9% components has at most about 99.7% availability. Redundancy (parallel copies) improves it.
  • Latency targets are percentiles (p95/p99), not averages.
  • Durability (data never lost) is different from availability (system answers); S3 is designed for 11 nines of durability.
  • RPO (how much data you can lose) and RTO (how long recovery may take) drive backup and DR design.
  • Other requirements to ask about: consistency needs, data residency, compliance (GDPR, HIPAA, PCI), security, cost budget, team size.

Worked example: URL shortener

  • 100 million new URLs per month ÷ 2.6 million seconds ≈ 40 writes/second.
  • Reads at 100:1 → ≈ 4,000 reads/second average, ~12,000 at peak (3×).
  • Storage: 100M × 12 months × 5 years = 6 billion records × ~500 bytes ≈ 3 TB.
  • Keyspace: base62 with 7 characters = 62^7 ≈ 3.5 trillion codes, plenty for 6 billion.
  • Conclusion: reads dominate → cache hot links; a key-value store handles the data comfortably.

Worked example: chat messages

  • 10 million daily users × 40 messages = 400 million messages/day ÷ 86,400 ≈ 4,600/second, ~14,000 at peak.
  • 400M × 200 bytes = 80 GB/day ≈ 29 TB/year before replication and indexes.
  • Conclusion: partition messages by conversation; plan retention or tiering; the real challenge is connection count and fan-out, not raw storage.

Worked example: photo uploads

  • 1 million uploads/day × 2 MB = 2 TB/day ≈ 730 TB/year → object storage with lifecycle tiers, CDN for reads.
  • Ingress ≈ 2 TB ÷ 86,400 s ≈ 23 MB/s average; upload directly to object storage with pre-signed URLs to keep it off app servers.

Interview angle: say what each number changes in the design ("4,000 reads per second is fine for a cache plus one database; 400,000 would push us to sharding").

Read-throughCache loads from DB itselfCleaner app code; cache layer must know the source
Write-throughWrite to cache and DB togetherFresh cache; slower writes
Write-behindWrite to cache, flush to DB laterFast writes; risk of data loss

Partitioning (sharding)

  • Hash partitioning: even spread; range queries become scatter-gather.
  • Range partitioning: efficient ranges; risk of hot ranges (e.g. recent timestamps).
  • Directory/lookup: flexible placement (tenant → shard map); the map is a dependency.
  • Consistent hashing: adding or removing a node moves only about 1/N of keys; virtual nodes even out load.
  • Choose the key from access patterns (tenant ID, user ID, conversation ID); avoid keys that create hot partitions.

Replication

  • Leader-follower: writes to one leader, reads from replicas (replication lag → read-your-writes issues).
  • Multi-leader: writes in several regions; conflict resolution needed.
  • Leaderless (quorum): writes to W of N replicas, reads from R; R + W > N gives overlap (Dynamo-style).
  • Synchronous replication protects data but adds latency; asynchronous is faster but can lose recent writes on failover.

Consistency, CAP and PACELC

  • CAP: during a network partition, a distributed system must choose between consistency (refuse or delay some requests) and availability (answer, possibly with stale data). Partitions aren't optional, so the real choice is CP vs AP behaviour during failures.
  • PACELC: if Partitioned, choose Availability or Consistency; Else (normal operation), choose Latency or Consistency. It explains why systems trade consistency for speed even without failures.
ModelGuaranteeExample need
Strong / linearizableEvery read sees the latest writeAccount balances, inventory reservation, unique usernames
Read-your-writesA user sees their own changes immediatelyProfile edits, posting a comment
Monotonic readsA user never sees data go backwardsFeeds, chat history

Interview angle: pick consistency per feature, not per system ("payments strongly consistent; the feed eventually consistent with read-your-writes for the author").

Scaling and resilience patterns

Scale out

Stateless services behind a load balancer; autoscale on the right signal (CPU or requests for APIs, queue age for workers).

Read scaling

Caches, read replicas, CDNs, denormalised read models (CQRS) for heavy read paths.

Write scaling

Partitioning, batching, async processing via queues, append-only designs, write-optimised stores.

Async processing

Return 202 and process in the background for slow work; notify on completion.

Timeouts

Every remote call has one; deeper calls get shorter timeouts than their callers.

Retries

Only for transient failures, with exponential backoff and jitter, capped, and only on idempotent operations (or with idempotency keys).

Circuit breakers

Fail fast when a dependency is down; try again after a cool-down.

Bulkheads

Separate pools (connections, threads, queues) per dependency or tenant so one failure doesn't drain everything.

Backpressure and load shedding

Bounded queues, 429/503 with Retry-After, shed low-priority work under overload.

Graceful degradation

Serve cached or partial results, disable non-critical features via flags.

Data patterns across services

  • Database per service for independent evolution; no shared tables between teams.
  • Sagas replace distributed transactions: a sequence of local transactions with compensating actions; orchestration (central coordinator, e.g. Step Functions) vs choreography (services react to events).
  • Outbox for reliable event publishing; idempotent consumers for duplicates.
  • Avoid two-phase commit across services (blocking, poor availability).
  • Strangler fig for migrating monoliths incrementally.
  • Event sourcing (store events as the source of truth) only when history and audit justify the complexity.

Trade-off phrases that help

  • "We trade some freshness for read latency here; a 60-second TTL is acceptable for this view."
  • "This is the single point of failure; we mitigate with Multi-AZ failover, accepting about a minute of write unavailability."
  • "I'd start with the simpler option and switch when we see metric X cross threshold Y."
  • "This choice costs more to run but removes an operational burden the team can't staff."
