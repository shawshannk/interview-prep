Cloud basics

ConceptWhat it means
RegionA geographic area (e.g. ap-south-1 Mumbai) with independent infrastructure. Choose for latency, data residency, service availability and price.
Availability Zone (AZ)One or more isolated data centres inside a region with separate power and networking. Spread production across at least two AZs.
Edge locationsCDN and DNS points of presence (CloudFront, Route 53) closer to users.
IaaS / PaaS / SaaS / FaaSYou manage less as you move right: VMs (EC2) → managed platforms (Elastic Beanstalk, App Service) → finished software → functions (Lambda).
Shared responsibilityThe provider secures the cloud (hardware, facilities, managed-service internals); you secure what you put in it (IAM, data, network rules, patching your OS and code, encryption settings). The split moves toward the provider for managed services.
Well-Architected pillarsOperational excellence, security, reliability, performance efficiency, cost optimisation, sustainability.

ComponentPurpose
VPCYour private network in a region, defined by a CIDR block (e.g. 10.0.0.0/16 = 65,536 addresses).
SubnetA slice of the VPC in one AZ. "Public" means its route table sends 0.0.0.0/0 to an Internet Gateway.
Route tableDecides where traffic from a subnet goes.
Internet GatewayTwo-way internet access for resources with public IPs.
NAT GatewayOutbound-only internet access for private subnets (pulling packages, calling APIs). Charged per hour and per GB; one per AZ for resilience.
Security groupStateful, instance/ENI-level allow rules. Reference other security groups instead of IP ranges ("app SG can reach DB SG on 5432").
Network ACLStateless subnet-level allow/deny rules; rarely the main control.
VPC endpointsPrivate access to AWS services: gateway endpoints for S3 and DynamoDB (free), interface endpoints (PrivateLink) for others. Reduce NAT cost and keep traffic off the internet.
Peering / Transit GatewayConnect VPCs: peering is point-to-point and non-transitive; Transit Gateway is a hub for many VPCs and on-premises links.
VPN / Direct ConnectEncrypted tunnel over the internet / dedicated private line to on-premises.

CIDR quick math: /16 = 65,536 addresses, /24 = 256, /28 = 16. AWS reserves 5 addresses in each subnet.

Identity and access (IAM)

  • Principals: users (avoid long-lived ones), roles (temporary credentials, assumed by services, people via SSO, CI pipelines via OIDC), and service principals.
  • Policies: JSON documents with Effect, Action, Resource and optional Condition. Identity-based policies attach to principals; resource-based policies (S3 bucket policy, KMS key policy, SQS policy) attach to resources and can grant cross-account access.
  • Evaluation: everything is denied by default; an explicit Deny anywhere wins; otherwise an Allow is needed, and organisation guardrails (SCPs) and permission boundaries cap what can be allowed.
  • Least privilege: one role per workload; scope actions and resources; use conditions (source VPC, tags, MFA).
  • No secrets in code: workloads use roles; CI uses OIDC federation (e.g. GitHub Actions assuming a role) instead of access keys.
  • Multi-account setup: separate accounts per environment or team under AWS Organizations, with central logging and SSO.
{
  "Effect": "Allow",
  "Action": ["s3:GetObject"],
  "Resource": "arn:aws:s3:::reports-bucket/tenant-42/*",
  "Condition": { "Bool": { "aws:SecureTransport": "true" } }
}

Choosing compute

OptionBest forWatch out for
Lambda / FunctionsEvent-driven, spiky or low traffic, glue code, scheduled jobsCold starts, 15-minute limit, concurrency limits and downstream DB connections, cost at steady high load
ECS Fargate / Container AppsLong-running APIs and workers in containers without managing nodesPer-task pricing higher than raw EC2; still need autoscaling and health checks
EKS / AKSMany services, platform team, portability, advanced schedulingSignificant operational overhead; upgrades, add-ons, security
EC2 / VMsSpecial hardware, licensing, legacy software, full controlPatching and scaling are yours
App Runner / App ServiceSimple web apps and APIs with minimal setupFewer knobs; check networking features

Pricing models: on-demand; Savings Plans / Reserved Instances for steady baseline (big discounts for 1–3 year commitments); Spot for interruptible work (batch, CI runners) at large discounts.

Autoscaling signals: CPU or request count per target for APIs; queue depth or age for workers; scheduled scaling for known peaks.

Storage and databases in the cloud

  • S3 storage classes: Standard → Standard-IA / One Zone-IA → Glacier Instant/Flexible/Deep Archive; Intelligent-Tiering moves objects automatically. Use lifecycle rules.
  • S3 essentials: Block Public Access on; encryption on by default (SSE-S3; use SSE-KMS for key control); versioning for protection; pre-signed URLs for direct upload/download; event notifications to trigger processing.
  • RDS / Aurora: Multi-AZ for high availability (standby failover, about a minute or two); read replicas for read scaling; automated backups with point-in-time restore; RDS Proxy to pool connections (useful with Lambda).
  • DynamoDB: on-demand vs provisioned capacity; design keys for access patterns; TTL for expiry; Streams for change events; global tables for multi-region.
  • Backups: AWS Backup for policies across services; test restores regularly.

Infrastructure as Code (Terraform)

IaC makes environments reproducible, reviewable and auditable. Terraform (or OpenTofu) is cloud-agnostic; CloudFormation/CDK and Bicep are native options.

Containers and Kubernetes basics

Containers

  • Image vs container: an image is an immutable, layered filesystem plus metadata; a container is a running instance with its own process space and network namespace sharing the host kernel.
  • Good images: multi-stage builds, small base images, non-root user, pinned versions, no secrets baked in, one main process, logs to stdout.
  • Registries: ECR / ACR; scan images for vulnerabilities; tag immutably (commit SHA), not just latest.

Kubernetes objects to know

Deployment / ReplicaSetDesired number of identical pods; rolling updates and rollbacks.

  • Continuous integration: small, frequent merges to main with a fast, reliable pipeline.
  • Continuous delivery keeps main always deployable (manual approval to release); continuous deployment releases every passing change automatically.
  • Build once, deploy many: the same artifact goes to every environment; configuration differs.
  • Pipeline security: OIDC to the cloud, least-privilege deploy roles, protected branches, required reviews, signed artifacts where needed.
  • Database migrations: backward-compatible (expand → migrate → contract) so app and schema can roll independently.

Operations: observability, security, cost

Observability

Structured logs with correlation IDs; metrics (RED for services: rate, errors, duration; USE for resources: utilisation, saturation, errors); distributed traces (OpenTelemetry). Alert on symptoms tied to SLOs, not every cause.

Security baseline

MFA and SSO, no root usage, CloudTrail everywhere, GuardDuty/Security Hub, encryption at rest and in transit, private subnets for data, WAF on public endpoints, secrets in a manager with rotation.

Cost drivers

Idle compute, oversized instances, NAT data processing, cross-AZ and internet egress, log ingestion volume, unattached volumes and old snapshots, unbounded LLM usage.

Cost controls

Tags for ownership, budgets and anomaly alerts, rightsizing, Savings Plans for baseline, Spot for batch, lifecycle rules, VPC endpoints, per-team cost visibility (FinOps).
