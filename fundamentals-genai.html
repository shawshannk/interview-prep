How LLMs work (the engineer's view)

ConceptWhat you need to know
TokensModels read and write sub-word tokens. Roughly 1 token ≈ 4 characters ≈ 0.75 English words; other languages and code often use more tokens. Pricing, limits and latency are all per token.
Next-token predictionA transformer predicts a probability distribution over the next token, appends the chosen one and repeats. Output is generated one token at a time, which is why streaming helps perceived latency.
Context windowMaximum tokens of input plus output per call. Larger windows cost more and quality can drop for facts buried in the middle of long contexts.
Temperature / top-pSampling controls. Low temperature for extraction and classification (more deterministic), higher for creative text. Even temperature 0 isn't guaranteed to be perfectly deterministic.
System / user / assistant messagesRoles in a chat request. The system prompt sets behaviour and constraints; it is not a security boundary.
HallucinationFluent but unsupported output. Reduce with grounding (RAG), constrained output, asking for citations, allowing "I don't know", and evaluation — not with prompting alone.
Knowledge cutoffModels don't know events after training; supply current data in the context.
Reasoning modelsSpend extra tokens "thinking" before answering; better at multi-step problems, slower and more expensive.
MultimodalMany models accept images/documents as input; useful for document extraction.

Interview angle: "Facts → RAG; behaviour/format → prompting, then fine-tuning if needed; actions → tools." Mention that you'd measure with an eval set before and after each change.

Prompting fundamentals

  • Be specific: task, audience, constraints, what to do when information is missing.
  • Give examples (few-shot) of good input/output pairs, including edge cases.
  • Structure input with clear delimiters or XML-style tags separating instructions, context documents and user input.
  • Ask for structured output (JSON schema) and validate it in code; use the provider's structured-output or tool features where available.
  • Let it think for complex tasks (step-by-step reasoning or a reasoning model), but parse only the final answer.
  • Version prompts like code, with tests (eval sets) that run on every change.
  • Keep stable content first (system prompt, instructions, reference docs) so prompt caching can reuse it.

Embeddings and vector search

  • Embedding: a fixed-length vector (often 256–3,072 dimensions) representing the meaning of text; similar meaning → nearby vectors.
  • Similarity: cosine similarity (angle) or dot product; with normalised vectors they rank the same.
  • Approximate nearest neighbour (ANN): exact search is too slow at scale; indexes like HNSW (graph-based, fast, memory-hungry) or IVF (clustering) trade a little recall for speed.
  • Vector stores: pgvector (PostgreSQL), OpenSearch, Azure AI Search, Pinecone, Qdrant, Weaviate, S3 Vectors VERIFY (availability per region). Choose for filtering support, scale, operations and cost; pgvector is a strong default if you already run Postgres.
  • Same model for indexing and queries; changing the embedding model means re-embedding everything.
  • Hybrid search: combine keyword (BM25) and vector results (e.g. reciprocal rank fusion). Keywords catch exact IDs, codes and names that embeddings miss.

Tool use and agents

  • Tool calling: you describe functions with a JSON schema; the model returns a structured call; your code validates arguments, checks permissions, executes, and returns the result for the next model turn.
  • Agent loop: model plans → calls tools → observes results → repeats until done. Set limits on steps, time and cost.
  • Workflows vs agents: prefer a fixed workflow (deterministic steps with LLM calls inside) when the path is known; use agents when the steps truly vary.
  • Guardrails: least-privilege tools, read-only by default, human approval for irreversible actions (payments, emails, deletes), idempotency, full audit logs.
  • MCP (Model Context Protocol): an open standard for connecting models to tools and data sources through servers, so integrations are reusable across clients.

Evaluation

Without evaluation, every prompt or model change is a guess. Build an eval set early (50–200 real, representative questions with expected answers or criteria) and run it in CI.

What to measureExamples
Retrieval qualityRecall@k (is the right chunk in the top k?), MRR / nDCG (is it ranked high?)
Answer qualityFaithfulness/groundedness (claims supported by context), answer relevance, correctness vs reference, citation accuracy
SafetyPrompt-injection resistance, PII leakage, refusal correctness, toxicity
OperationalLatency (time to first token, total), cost per request, error/timeout rate
BusinessTask success, deflection rate, user ratings, escalation rate
  • Methods: exact/programmatic checks where possible; LLM-as-judge with a clear rubric (calibrate against human labels); human review of samples.
  • Online: log prompts, retrieved chunks, outputs and feedback (with privacy controls); A/B test changes.
  • Frameworks: RAGAS, DeepEval, promptfoo, Bedrock/Azure evaluation features, or a simple in-house harness.

Cost and latency

  • Cost = input tokens × input price + output tokens × output price (output usually costs several times more). Example: 2,000 input + 300 output tokens per request × 100,000 requests/day = 230 million tokens/day; multiply by your model's prices.
  • Levers: right-size the model (route easy requests to a small model), trim context (fewer, better chunks), prompt caching for repeated prefixes, response caching for repeated questions, batch APIs for offline work, cap max output tokens.
  • Latency: stream responses; minimise sequential LLM calls; run retrieval and other lookups in parallel; smaller models for intermediate steps; set timeouts with fallbacks.
  • Throughput limits: providers enforce tokens/requests per minute; plan quotas, use retries with backoff, consider provisioned throughput for steady high volume.
  • Bedrock specifics: one API (Converse) across model families, Knowledge Bases, Guardrails, Agents, on-demand vs provisioned throughput, cross-region inference profiles VERIFY (current feature names).
