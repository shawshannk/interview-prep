async / await in one paragraph

An async method is compiled into a state machine. At an await on an incomplete task, the method returns to its caller and the rest runs later as a continuation; no thread is blocked while waiting for I/O. Task represents the operation; ValueTask avoids allocation when results are often synchronous (await it once only). ConfigureAwait(false) skips resuming on the captured synchronisation context (mainly relevant in libraries and UI apps; ASP.NET Core has no synchronisation context). Pass CancellationTokens through. Never block on async code with .Result or .Wait() (thread-pool starvation, deadlocks in UI contexts), and avoid async void except for event handlers.

Practise: .NET Backend bank (N001–N020 for basics, async internals throughout).

.NET runtime and versions

  • CLR: runs IL code; the JIT compiles methods to machine code at first call; tiered compilation starts with quick code and recompiles hot methods with optimisations (dynamic PGO uses runtime data). ReadyToRun precompiles to cut start-up; Native AOT compiles ahead of time (fast start, smaller memory, but no runtime code generation and limited reflection).
  • Garbage collector: generations 0, 1, 2; objects of 85,000 bytes or more go to the Large Object Heap (collected with gen 2); server GC (per-core heaps, throughput) vs workstation GC; Span<T>, ArrayPool and stackalloc reduce allocations.
  • Thread pool: grows gradually when work is blocked; blocking calls in async code cause starvation (rising latency with low CPU).
  • Release cadence: a new major version every November; even numbers are LTS (3 years), odd numbers are STS. .NET 8 (LTS) and .NET 9 (STS) both reach end of support in November 2026; .NET 10 (LTS, November 2025) is the upgrade target VERIFY.
  • Diagnostics: dotnet-counters (live metrics), dotnet-trace (profiling), dotnet-dump (memory/threads), EventPipe, OpenTelemetry via ActivitySource and Meter.

ASP.NET Core

Request pipeline

Kestrel→Exception handling→HTTPS / HSTS→Static files→Routing→CORS→Authentication→Authorization→Rate limiting→Endpoint

Middleware runs in registration order on the way in and reverse order on the way out; order matters (authentication before authorization, CORS before auth for preflights, exception handling first).

Other essentials

  • Configuration: layered providers (appsettings.json, environment-specific files, environment variables, secrets); bind to classes with the Options pattern (IOptions fixed, IOptionsSnapshot per request, IOptionsMonitor live changes).
  • Minimal APIs vs controllers: minimal APIs are lighter and fast; controllers suit large APIs with filters and conventions. Both share routing, DI, auth.
  • Validation: model binding plus validation attributes or FluentValidation; return 400/422 with Problem Details.
  • AuthN/AuthZ: JWT bearer or cookie schemes; policies and requirements; resource-based authorization for object ownership.
  • HttpClient: use IHttpClientFactory (handler pooling, DNS refresh) with resilience handlers (timeouts, retries, circuit breaker).
  • Background work: BackgroundService/IHostedService; create scopes for scoped services; handle shutdown via cancellation tokens.
  • Health checks: liveness (process alive) vs readiness (dependencies reachable) endpoints.

Practise: .NET Backend bank (DI, configuration, auth, middleware).

EF Core and data access

  • DbContext is a unit of work with a change tracker; register it as scoped; it is not thread-safe (no parallel queries on one context).
  • Tracking: loaded entities are tracked for updates; use AsNoTracking() for read-only queries (faster, less memory).
  • Loading related data: eager (Include), explicit, or lazy (proxies; risks N+1 queries). Watch for N+1: loading a list then querying per item.
  • Cartesian explosion: multiple collection Includes multiply rows; use AsSplitQuery() or projections.
  • Projections (Select into DTOs) fetch only needed columns and skip tracking.
  • Raw SQL: FromSql/FromSqlInterpolated parameterise; FromSqlRaw with concatenation is an injection risk.
  • Concurrency: concurrency tokens (rowversion) → DbUpdateConcurrencyException on conflicting updates.
  • Migrations: generated from model changes; review the SQL; for large tables use expand/contract steps and batched backfills.
  • Bulk operations: ExecuteUpdate/ExecuteDelete (EF Core 7+) run set-based SQL without loading entities.
  • Dapper vs EF Core: Dapper is a thin mapper for hand-written SQL (full control, fast); EF Core gives modelling, change tracking and migrations. Many teams use both.

Practise: .NET Backend bank (EF Core questions), Data Layer bank.

Node.js and TypeScript

Event loop

Node runs JavaScript on one main thread. I/O is handed to the OS or to libuv's thread pool (default 4 threads; used for file system, DNS lookup, crypto, compression). Completed work queues callbacks that run on the main thread.

timerssetTimeout→pending callbacks→pollI/O callbacks→checksetImmediate→close callbacks

Between callbacks, process.nextTick callbacks run first, then promise microtasks. A long synchronous task (big JSON parse, a CPU loop, a sync regex) blocks every request. Fixes: break work up, use worker threads, or move it to another service.

  • Streams process data in chunks with backpressure (pipeline() handles errors and cleanup).
  • Errors: unhandled promise rejections crash the process in modern Node; always handle async errors; graceful shutdown on SIGTERM.
  • Modules: CommonJS (require) vs ES modules (import); ESM is the standard direction.
  • Scaling: one process per core (cluster, PM2, or several containers); state goes in external stores.

TypeScript

  • Structural typing: compatibility by shape, not by declared name.
  • Types are erased at runtime: validate external input (zod, class-validator) because types don't check data from the network.
  • unknown over any; strict mode on; discriminated unions for state; generics and utility types (Partial, Pick, Omit, Record).

Practise: Node & NestJS bank.

SQL Server

  • Clustered index = the table's physical order (one per table, usually the primary key). Nonclustered indexes point to the clustered key; INCLUDE columns make them covering and avoid key lookups.
  • SARGable predicates let the optimiser seek an index: avoid functions on indexed columns (WHERE YEAR(CreatedAt) = 2025 → use a date range), implicit conversions, leading wildcards.
  • Execution plans: look for scans on large tables, key lookups, big estimate vs actual gaps (stale statistics), sorts and spills, parallelism.
  • Statistics drive cardinality estimates; out-of-date stats cause bad plans.
  • Parameter sniffing: a plan compiled for one parameter value is reused for very different values; fixes include OPTION (RECOMPILE), OPTIMIZE FOR, or query redesign.
  • Locking: shared/exclusive locks, lock escalation, blocking chains, deadlocks (one victim chosen); RCSI (read committed snapshot) uses row versions in tempdb so readers don't block writers.
  • Query Store keeps plan and runtime history; force a known good plan after a regression.
  • Transaction log: every change is logged; long transactions and missing log backups (full recovery model) grow the log.

Practise: Data Layer bank (Q001–Q030 for basics).

PostgreSQL

  • MVCC: updates create new row versions; old versions are cleaned by VACUUM (autovacuum). Long-running transactions prevent cleanup and cause bloat.
  • Index types: B-tree (default), GIN (jsonb, arrays, full-text), GiST (geometric, ranges, exclusion constraints), BRIN (huge naturally ordered tables), hash; partial and expression indexes.
  • EXPLAIN (ANALYZE, BUFFERS) shows actual timings and I/O.
  • jsonb stores binary JSON that can be indexed with GIN; good for flexible attributes alongside relational columns.
  • Connections are processes (each uses memory); use a pooler (PgBouncer, RDS Proxy) when many clients or Lambdas connect.
  • Extensions: pgvector (vector search), PostGIS (geospatial), pg_stat_statements (query statistics).
  • Replication: streaming (physical) replicas for reads and failover; logical replication for selective tables and upgrades.
  • Default isolation is Read Committed; Serializable uses SSI and can abort transactions that would conflict (retry them).

Practise: Data Layer bank.

Redis

  • In-memory data structures: strings, hashes, lists, sets, sorted sets (leaderboards, rate limit windows), streams, plus geo and probabilistic types.
  • Commands run one at a time on the main thread (I/O threads exist in newer versions), so each command is atomic; slow commands (KEYS *, huge values) block everyone.
  • Expiry with TTLs; eviction policies when memory is full (default noeviction returns errors; caches usually use allkeys-lru or allkeys-lfu).
  • Persistence: RDB snapshots and/or AOF log; as a cache, plan for data loss.
  • Patterns: cache-aside, rate limiting (INCR + EXPIRE, Lua for atomic logic), sessions, pub/sub (fire and forget), distributed locks (be careful: need fencing tokens for correctness).
  • Cluster mode: keys spread across 16,384 hash slots; multi-key operations need keys in the same slot (hash tags {user:1}).
  • Cache problems: stampede (many misses at once → lock or early refresh), stale data (TTL plus invalidation on writes), hot keys.

Practise: Data Layer bank (Redis questions, Q090 caching culture).

DynamoDB

  • Keys: partition key (hash, spreads data) + optional sort key (range queries within a partition). Design keys from access patterns first.
  • Query reads one partition key (efficient); Scan reads the whole table (avoid in request paths).
  • Secondary indexes: GSIs (different keys, eventually consistent, own capacity); LSIs (same partition key, different sort key; defined at table creation).
  • Limits: item size 400 KB; per-partition throughput limits (roughly 3,000 read and 1,000 write units per second), so avoid hot keys VERIFY.
  • Capacity: on-demand (pay per request) or provisioned with auto scaling.
  • Consistency: eventually consistent reads by default; strongly consistent reads available on the table and LSIs, not GSIs.
  • Transactions across up to 100 items VERIFY; conditional writes for optimistic concurrency and uniqueness.
  • Streams capture changes for event processing; TTL deletes expired items in the background (not immediately).
  • Single-table design stores several entity types with generic keys (PK/SK) to serve many access patterns with few queries; powerful but harder to evolve.

Practise: Data Layer bank (DynamoDB modelling).

Messaging: queues and streams

Queue (SQS, Service Bus queues, RabbitMQ)Log / stream (Kafka, Kinesis, Event Hubs)
ConsumptionEach message processed by one consumer, then deletedMessages retained; each consumer group reads independently with its own offset
ReplayNo (except dead-letter redrive)Yes, within retention
OrderingBest effort (SQS standard); FIFO queues with message groupsPer partition (key decides the partition)
ScalingAdd consumers freelyParallelism limited by partition count per group
Typical useWork queues, background jobsEvent streaming, multiple subscribers, event sourcing, analytics
  • SQS: visibility timeout (message hidden while processed; reappears if not deleted), dead-letter queue after N receives, long polling, at-least-once delivery (standard), FIFO with deduplication and message groups VERIFY (current throughput limits).
  • SNS fans out one message to many subscribers; EventBridge routes events by rules and integrates SaaS/AWS sources.
  • Kafka: topics split into partitions; producers choose partition by key; consumers in a group share partitions (one consumer per partition); commit offsets after processing for at-least-once.
  • Delivery semantics: at-most-once (may lose), at-least-once (may duplicate, the common choice), exactly-once (only within specific boundaries); design idempotent consumers.
  • Outbox pattern: write the event to a table in the same transaction as the data change, then publish from the table, so you never save without publishing (or publish without saving).

Practise: Architecture bank (outbox, sagas, Kafka), Cloud & DevOps bank (SQS, EventBridge).

React and Next.js

React

  • Components are functions of props and state returning UI. State changes trigger a re-render of that component and its children; React reconciles the new tree with the old and updates the DOM minimally.
  • Keys identify list items across renders; use stable IDs, not array indexes, for dynamic lists.
  • Hooks rules: call at the top level, same order every render. useState, useEffect (synchronise with external systems; not for deriving data), useMemo/useCallback (memoise when it measurably helps), useRef, context.
  • Common bugs: missing effect dependencies (stale values), effects that set state on every render (loops), defining components inside components (remounts), mutating state directly.
  • React 18/19: concurrent rendering, automatic batching, transitions (useTransition), Suspense for data; React 19 adds Actions, useActionState, useOptimistic, and the React Compiler can auto-memoise VERIFY.

Next.js App Router

  • Server Components (default) render on the server, can access data directly, ship no JS for themselves; Client Components ("use client") handle interactivity and state.
  • Rendering: static (build time), dynamic (per request), streaming with Suspense; revalidation for incremental static regeneration.
  • Caching layers (request memoisation, data cache, full route cache, router cache) changed between versions; know how to opt out and revalidate VERIFY (behaviour for your version).
  • Server Actions are public HTTP endpoints: authenticate and authorise inside every action; validate input.
  • Middleware runs at the edge for redirects and light checks; never rely on it as the only authorization (see CVE-2025-29927).

Practise: Frontend bank.

Docker and containers

  • Image = read-only layers built from a Dockerfile; container = a running instance with a writable layer. Containers share the host kernel (namespaces and cgroups isolate them); they are not VMs.
  • Layer caching: order instructions from least to most frequently changing (copy dependency manifests and restore before copying source).
  • Multi-stage builds: build with the SDK image, copy only the output into a small runtime image (smaller, fewer vulnerabilities).
  • Security: run as non-root, read-only filesystem where possible, minimal base images (distroless, chiseled .NET images, alpine/slim), scan images, pin base image digests.
  • Signals: the main process is PID 1 and must handle SIGTERM for graceful shutdown (exec-form ENTRYPOINT, or an init like tini).
  • Config: environment variables and mounted secrets, not baked into images; .dockerignore keeps secrets and build junk out of the context.
  • Health checks in the orchestrator (ECS, Kubernetes) rather than only Docker's HEALTHCHECK.
# .NET multi-stage example
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src
COPY *.csproj ./
RUN dotnet restore
COPY . .
RUN dotnet publish -c Release -o /app

FROM mcr.microsoft.com/dotnet/aspnet:8.0
WORKDIR /app
COPY --from=build /app .
USER app
ENTRYPOINT ["dotnet", "Api.dll"]
